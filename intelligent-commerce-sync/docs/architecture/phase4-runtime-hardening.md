# Phase 4C.4: Runtime Hardening & Infrastructure Reliability
## Recovery, Durable Dispatch Scheduler, and Aggregated Health

---

## 1. Architectural Objective

Phase 4C.4 provides resilient execution infrastructure hardening around the certified execution contracts of Phase 4C.1, 4C.2, and 4C.3. It bridges asynchronous BullMQ queue execution with PostgreSQL persistence through four core services:

1. **`StaleProcessingRecoveryService`**: Concurrency-safe recovery of stale `PROCESSING` jobs without recomputing business intent or directly invoking marketplace operations during recovery. Any subsequent execution remains governed by the certified durable execution and idempotency contracts.
2. **`DurableDispatchScheduler`**: Reconciliation of persisted `PENDING` jobs with BullMQ queue jobs without re-computing business logic or generating duplicate queue identities.
3. **`RuntimeHealthService`**: Non-leaking aggregated health inspection across PostgreSQL, Redis, BullMQ queue, and SyncJob operational states.
4. **`RuntimeMaintenanceService`**: Orchestrator executing the recovery-dispatch-health cycle both on-demand and on a non-overlapping periodic timer using standard Node.js primitives (zero cron dependencies).

---

## 2. Invariants & Boundaries

### 2.1 Persistence Invariants
- **Zero Schema Migrations**: Operates completely within existing schema entities (`SyncJob`, `SyncEvent`, `AuditLog`, `IdempotencyRecord`).
- **Targeted Entity Mutability**: Runtime code may mutate only `SyncJob`, `SyncEvent`, and `AuditLog`. It MUST NOT mutate `Product`, `ProductSource`, `SourceVariant`, `SourceSnapshot`, `MarketplaceListing`, `MarketplaceListingVariant`, or `IdempotencyRecord`.
- **Payload Immutability**: `SyncJob.executionPayload` is the authoritative durable execution intent and is zero-mutated by recovery or scheduler.
- **Audit Log Cleanliness**: AuditLog entries generated by runtime services use:
  - `actorType = "SYSTEM"`
  - `actorId = "phase4c4-runtime-maintenance"`
  - `entityType = "SyncJob"`
  - `entityId = syncJob.id`
  No connection strings, credentials, access tokens, source payloads, gateway commands, or raw error objects are ever persisted into `before`, `after`, or `metadata`.

### 2.2 Queue Invariants
- **Deterministic Queue Job Identity**: BullMQ job IDs are derived strictly via `generateQueueJobId(syncJob.idempotencyKey)`. No randomness, timestamps, or attempt counters are appended.
- **Minimal Queue Payload**: BullMQ payload remains strictly `{ schemaVersion: 1, syncJobId }`. Redis never stores business data, prices, stock, or credentials.

## 3. Stale Processing Recovery

### 3.1 Qualification & Immutable Cutoff
A SyncJob is a candidate for stale recovery if and only if:
- `status === "PROCESSING"`
- `updatedAt <= cutoff` where `cutoff = now - staleProcessingMs`

> **Note on `updatedAt`**: Under the locked database schema, `updatedAt` is only a persisted age signal, not a heartbeat. A conservative `staleProcessingMs` threshold (300,000 ms / 5 minutes; minimum 60,000 ms) reduces premature-recovery risk, and observing a BullMQ `active` state blocks automatic recovery. However, under distributed processing, no exact distributed worker-liveness guarantee exists.
>
> **Immutable Cutoff Guarantee**: At the start of each recovery batch, `now` and `cutoff` are computed exactly once. The identical cutoff is used for candidate selection and conditional transaction claims. It is never recomputed per candidate or inside individual transactions.

### 3.2 Normalized BullMQ Job State Reconciliation
For each candidate, the BullMQ job is inspected via `syncQueue.getJob(generateQueueJobId(candidate.idempotencyKey))`. Conceptual states are normalized:

| Normalized Queue State | Recovery Action | Domain State Transition | Rationale |
|---|---|---|---|
| `active` | `SKIPPED_ACTIVE` | None (`PROCESSING`) | Worker actively holds the BullMQ job; do not interrupt in-flight execution. |
| `missing` (null) | `RECOVERED` | `PROCESSING -> FAILED -> PENDING` | Missing BullMQ job may indicate a crash window or lost queue state, but does not prove worker death. Safe to return to PENDING under runtime recovery policy. |
| `waiting`, `delayed`, `prioritized`, `failed` | `RECOVERED` | `PROCESSING -> FAILED -> PENDING` | Job is not actively running in a worker; safe to return to queueable state. |
| `completed` | `NEEDS_REVIEW` | `PROCESSING -> NEEDS_REVIEW` | Serious state conflict: queue completed but DB remained in `PROCESSING`. Manual operator review required; NEVER auto-replay. |
| `waiting-children`, `unknown` | `NEEDS_REVIEW` | `PROCESSING -> NEEDS_REVIEW` | Unsupported or unexpected state; fail closed. |

### 3.3 Concurrency-Safe Conditional Claim
To prevent races between multiple application instances, recovery uses a single Prisma transaction:
1. `updateMany` on `SyncJob` with `where: { id: candidate.id, status: "PROCESSING", updatedAt: { lte: cutoff } }`, setting status to `FAILED`.
2. If `count !== 1`, another instance won the claim. The transaction aborts with `CONCURRENT_SKIP`, generating zero extra events or audit logs.
3. Transition `FAILED -> PENDING` (asserted via `assertSyncJobTransition`).
4. Append `SYNC_FAILED` event with safe metadata: `{ errorCode: "STALE_PROCESSING_RECOVERED", recovery: true, queueState }`.
5. Append `AuditLog` with `action: "RECOVER_STALE_SYNC_JOB"`.

## 4. Durable Dispatch Scheduler

### 4.1 Dispatch Reconciler
The scheduler continuously ensures that `PENDING` SyncJobs in PostgreSQL have corresponding execution jobs in BullMQ.

Ordering is deterministic: `createdAt ASC, id ASC`, limited to `batchSize`.

For each `PENDING` job, the BullMQ job is inspected:
- **No queue job exists**: Calls certified `syncQueue.enqueueSyncJob(job.id)` -> `DISPATCHED`.
- **Queue job is `waiting`, `delayed`, `active`, or `prioritized`**: Already queued -> `ALREADY_QUEUED`. No duplicate is created.
- **Queue job is `failed`**: Concurrency-safe retry via `bullJob.retry()` -> `RETRIED`. If two schedulers race, the loser catches the retry exception, re-reads the state, and reports `ALREADY_QUEUED` cleanly if the job transitioned to `waiting` / `active`.
- **Queue job is `completed`**: Contradiction! DB is `PENDING` but queue says `completed`. The scheduler conditionally transitions `PENDING -> NEEDS_REVIEW` and records an AuditLog with `QUEUE_STATE_CONFLICT_NEEDS_REVIEW`.
- **Queue job is `waiting-children` or `unknown`**: Fail closed -> conditionally transition `PENDING -> NEEDS_REVIEW`.

## 5. Aggregated Runtime Health

`RuntimeHealthService` provides an operational snapshot without exposing sensitive credentials, connection URLs, or raw stack traces.

### 5.1 Health Classification Rules
- **`UNHEALTHY`**:
  - PostgreSQL base probe fails (`SELECT 1`), OR
  - Redis probe fails (reuses certified `checkRedisHealth()`), OR
  - BullMQ queue inspection fails (`getJobCounts()`), OR
  - SyncJob operational metrics inspection fails (fail closed; cannot falsely report HEALTHY).
- **`DEGRADED`**:
  - PostgreSQL, Redis, and queue are all healthy, AND
  - Stale `PROCESSING` jobs exist (`staleProcessing > 0`).
- **`HEALTHY`**:
  - PostgreSQL, Redis, and queue are all healthy, AND
  - `staleProcessing === 0` successfully verified.

Note: Business job failures (`FAILED` SyncJobs) represent domain outcomes and do not classify infrastructure as `UNHEALTHY`.

## 6. Maintenance Coordinator & Periodic Loop

`RuntimeMaintenanceService` coordinates operations:
1. **One-Shot Cycle (`executeCycle`)**:
   - Executes Recovery -> Scheduler -> Health Snapshot in order.
2. **Periodic Loop (`start` / `stop`)**:
   - Uses native `setInterval` with `.unref()` to avoid keeping processes alive.
   - Non-overlapping execution: if a tick occurs while a cycle is in-flight, it skips the tick (`skippedTicks`).
   - Exception handling: every cycle catches rejections, preventing unhandled promise rejections.
   - Graceful stop: `stop()` is asynchronous, clears the timer, prevents new ticks, awaits any active in-flight cycle, and resets state cleanly.

## 7. Test Queue & Namespace Cleanup Guarantees

- **Isolated Test Queues**: Every test runs against isolated queues prefixed with `phase4c4_test_*`.
- **Queue Obliteration**: In cleanup hooks, active workers are closed first, then queues are obliterated via BullMQ `rawQueue.obliterate({ force: true })`, followed by queue connection closure.
- **Bounded Redis Scan**: Lingering keys matching `bull:phase4c4_test_*` or `phase4c4_test_*` are scanned and removed via targeted `DEL`. Global destructive commands (e.g. `FLUSHDB`) and production queue keys are strictly forbidden.
- **PostgreSQL Isolation**: All database fixtures and created records are restricted to namespace prefix `phase4c4_test_*` and completely deleted in before/after lifecycle hooks.
